### 开发环境怎么搞

1. **构建工具**：这项目用的是 Maven，就这个 B 样了。
2. **JDK 版本**：必须是 **Java 22 或者更高**。你别拿个 JDK 8 过来，我操，真几把气人！
3. **IDE 设置**：为了让你那 B IDE 能认对项目结构，**别 NMB 直接开根目录 (`vulkan4j`)**。你得打开 `vulkan4j/modules` 这个目录当项目根目录，因为 `pom.xml` 在这儿呢，猪逼吧。你要是电脑太垃圾，也可以只开你要改的那个模块（比如 `vulkan4j/modules/ffm-plus`）。
4. **Git 设置**：你要是用 Windows，**在 clone 仓库之前**，先把 Git 配置里的 `core.autocrlf` 给关了。我再说一遍，是**之前**！这样能保证你 clone 下来的文件换行符是 LF。不然你一跑代码生成器，Git 就给你报 1145141919810 个没用的换行符改动，你 TM 还找 bug 呢，我草。

### 贡献流程

我们用的是“Fork & Pull Request”模式，就跟打野不来我怎么去一个道理，你得先有自己的东西：
1. Fork 这个仓库到你自己的号上。
2. 在你自己的仓库里改代码，然后 commit。
3. 对着我们这边的 `master` 分支，创建一个 Pull Request。

### 分支和 Commit

- **分支命名**：分支名里**别用斜杠 (`/`)**，会出一些很猪逼的 bug。用 `-` 或者 `_` 就行。其他的你爱叫啥叫啥，无所谓的。
- **PR 标题**：我们用的是 **Squash Merge**，意思就是你的 PR 标题会变成最后那条 commit 信息。所以你给我想个清楚点的标题，别写个“修了个 bug”，什么 B 标题啊，我操！

### 代码风格

1. **缩进**：所有 Java 和 Kotlin 代码都用 **4 个空格**缩进。
2. **行长度**：最好是 **100** 个字符，但你要是能说的道理，**120** 个也行。
3. **换行符**：所有文本文件都用 **LF** (`\n`)。
4. **保证文件末尾有个换行符**
5. **空安全注解**
   我们用 `org.jetbrains.annotations:26.0.2`。规矩是这样的：
    - **默认非空**：所有参数、返回值、字段，默认都是非空的。**我推荐你**加上 `@NotNull`，但不加也行。
    - **显式可空**：但如果一个东西**真的**可能是 `null`，你**必须**给我标上 `@Nullable`。你要是这点都整不明白，那你写什么 Java，写点 TypeScript 不好吗？

> 看看这儿：[`.editorconfig`](./.editorconfig)

### 测试你的 B 代码

1.  **`ffm-plus` 模块**
    这个模块有专门的单元测试。
    有些测试要你自己去 `misc/test_binary` 目录里跑脚本生成点东西才能跑。你要是不改这块，可以不弄，本地测试失败了无所谓的，反正 CI 会出手。

2.  **修改现有的 API 绑定**
    你要是改了现有的 API，记得去 `modules/example` 里把对应的例子也测了。CI 那破机器跑不了图形 API，全靠大伙儿自己测。你测得越明白，主播就越省事，懂不懂？

3.  **添加新的 API 绑定**
    加了新 API，就在 `modules/example` 里加个最简单的“自己吃自己狗粮”的测试，证明你这玩意能用。你要是不加，你这新 API 就会被标成**实验性**的，到时候别叫。

### `codegen-v2` 模块：怎么加新 API 绑定

你要给新的 C/C++ API 加绑定，按下面几步来：

1.  **准备输入文件**
    去 `codegen-v2/input` 里写个脚本，把头文件或者 XML 什么的下下来。记得用 tag 或者 commit hash 把版本锁死，别 NMB 每次都不一样。
    - 提示：可以用 `clang-format` 预处理一下头文件，让 `hparse` 和 `cdecl` 这俩模块好处理一点。

2. **写个 B 元数据提取器**
   在 `club.doki7.babel.extract` 下面给你新的 API 整个提取器。
    - **代码复用**：你要是看到别的提取器里有你想要的功能（比如解析结构体），**别 NMB 上来就想着复用**。我告诉你，大部分情况你应该**直接复制粘贴**代码到你的新模块里。我给你掰扯掰扯为什么：
      C++ 这 B 语言到处都是方言，每个 API 的提取要求都有点细微但很重要的差别。你要是直接 `import`，别人一改你就炸了，或者你一改别人就炸了。想搞个什么“统一”的解析器更是猪逼行为，会让代码变得巨 NMB 复杂，没法维护。
      只有当你觉得一个东西真的**通用到 NMB 离谱**（比如 `detectFunctionAlikeMacro` 这种），你再考虑把它抽到 `hparse` 或者 `cdecl` 里去。
    - **Nullability**：
        - 指针类型的函数参数，默认**可空**，除非有 `VMA_NOT_NULL` 说明它是非空的。
        - 结构体里的字段，默认**非空**，除非有什么东西说明它是可空的。这一块的 `vulkan` 和 `vma` 的提取器就整得很好，建议去看看。
    - **指向单个还是多个**：如果你 100% 确定一个指针参数只指向一个对象，就把它标成 `pointerToOne`。你不确定就别动，别瞎几把猜。
    - 提取器负责重命名，学学别人怎么写的。

3. **创建一个代码生成驱动**
   在 `club.doki7.babel.drv` 模块里，新建一个 Kotlin 文件，写个 `main` 函数来跑代码生成。参考下别的模块。

4. **验证对共享组件的修改**
   你要是改了 `hparse` 或 `cdecl` 这种公用的东西，**必须**把所有 API 的代码都重新生成一遍，看看你有没有把别人的东西搞炸。
